# 1.4.0 rollback plan

> **Historical schema scope:** the 0060 head references below describe the 2026-10-21
> preparation snapshot. PR #936 adds candidate migration `0061_money_instrument_links`;
> these steps are not a current-head runbook. Reconcile the selected candidate schema
> before any separately authorized runtime operation.

> **Status:** preparation aid for an unpublished candidate. It is not an authorization to stop,
> restore or change any runtime. Only the Owner/Integrator may select and execute a rollback.
>
> **Production rollback status: BLOCKED for a `0060 → 0058` return.** The accepted procedures
> can verify a matched `0058` code/database pair only in a fresh isolated target; none can
> replace the Stable database with a cross-schema backup. See section 5.

This plan covers a runtime that has installed the 1.4.0 candidate and schema
`0060_source_money_classifications`, and the decision to return to the published v1.3.0 runtime
at schema `0058_broker_money_ownership`. That return is currently not executable in production;
the decision is therefore between the blocked matched-pair restore and a forward fix. It
follows the release, backup and recovery rules in
[O3](../OWNER_RUNTIME_OPERATIONS.md#o3) and [O4](../OWNER_RUNTIME_OPERATIONS.md#o4), and the
Owner UAT boundary in [D4](../DEVELOPMENT.md#d4-ui_v2_owner_uat-5-assignment-and-backup-first).
The candidate slice is described in the [1.4.0 draft notes](../release-notes-1.4.0.md); the
validation run is in the [Test-run checklist](1.4.0-test-run.md).

## 1. Decision rule

Choose one of two paths before changing anything:

1. **Restore the matched pre-upgrade code/database pair.** This is the intended return to
   v1.3.0 code with a verified `0058` database, but the production route is **BLOCKED** with
   the existing accepted procedures: the in-app restore requires an exact same-schema database
   and the isolated recovery wrapper only writes a fresh non-Stable target. Do not attempt a
   production restore until a separately accepted cross-schema procedure exists (section 5).
2. **Fix forward on `0060`.** Use this when post-upgrade source-intake journal rows,
   classifications or other data must be retained. It is also the only executable production
   path once the database has been migrated to `0060`. Prepare and accept a new candidate with
   a new forward migration. Do not point old v1.3.0 code at the `0060` database.

Do not use an Alembic downgrade as a substitute for either path on production. A downgrade may
be useful on a disposable Test database (section 6), but it is not a supported production
rollback and it cannot recover data that is not in the backup.

## 2. Preconditions and recovery pair

- [ ] The exact candidate SHA, the previous published release identity, the Stable checkout,
      the assigned production database and a disjoint backup destination are explicitly known.
- [ ] A verified pre-upgrade backup exists from before the 1.4.0 update. Its SQLite
      `integrity_check` is `ok`, `alembic_version` is readable and its backup/recovery-point
      identity is recorded Owner-locally.
- [ ] A preservation copy/backup of the failed `0060` database and its logs is retained before
      any restore or replacement. This is evidence, not a rollback target; do not publish its
      contents.
- [ ] The runtime is stopped through its supported operation. Confirm no owned process is
      listening on `8000`; never kill an unrelated process by port.
- [ ] Only one profile is active. Do not run Stable and Preview/Test concurrently.
- [ ] The old code and old database remain a pair. v1.3.0 may open `0058`; it must never open
      `0059` or `0060`. The startup preflight fails closed on an ahead/unknown revision, and that
      failure must not be bypassed.

## 3. Failure classes and first action

| Situation | First action | Rollback implication |
|---|---|---|
| Failure before any database mutation (prepare/Validate, wrong SHA, wrong path, missing backup) | Stop. Preserve the error. Do not Start. | No database restoration is needed. If candidate code was pinned, OPS02 may repin the published v1.3.0 target against the unchanged `0058` database. |
| Startup migration fails or health never becomes ready | Stop the owned process. Preserve the database and logs. Do not retry blindly. | Preserve the verified pre-upgrade backup. Production restore is **BLOCKED** under current procedures (section 5); do not patch the half-migrated file, downgrade it or raw-copy over it. |
| `0060` starts but the page/API is wrong, or provisional data is unacceptable | Stop. Preserve the `0060` database and evidence. Decide restore vs forward fix. | Forward fix is the only executable production path. The matched `0058` restore is **BLOCKED** (section 5); if the pre-upgrade history must become production again, escalate for an accepted recovery procedure. |
| Financial Apply/Close/receipt or Stable data was changed unexpectedly | Stop immediately. Treat as a financial/data incident. | Preserve evidence and do not continue UAT. The matched-pair restore is **BLOCKED** (section 5); the Owner/Integrator must choose forward fix or authorize a separate recovery procedure. |
| Restore/ACK outcome is ambiguous or the target identity changed | Stop. Do not retry or reuse the target. | Follow O4 ambiguity rules: preserve evidence, reread authoritative state, and treat unknown as not success. |
| Secret/private data exposure | Stop; restrict the artifact; follow the Owner privacy process. | No technical rollback substitutes for containment and notification. |

## 4. Schema notes: 0058, 0059 and 0060

| Revision | Purpose | Rollback relevance |
|---|---|---|
| `0058_broker_money_ownership` | Published v1.3.0 head. | The database must be at this revision for a v1.3.0 runtime. |
| `0059_source_intake` | Durable source-intake journal, observations and append-only review commands. | Additive. A **populated** journal refuses downgrade with `cannot downgrade populated source intake journal`; only a backup restore could return to `0058`, and that production route is currently **BLOCKED** (section 5). |
| `0060_source_money_classifications` | Provisional Money classifications, unique by intake/reference and observation. | Additive. Downgrade drops the classification table only; the `0059` journal and financial tables are preserved. Re-upgrade recreates an empty table. Classification choices are lost and are not backfilled. |

Rules that apply:

- Upgrade is forward: `0058 → 0059 → 0060`. Both migrations are additive and do not rewrite
  existing journal or financial facts.
- `0060` downgrade is implemented and synthetically tested with a populated table. It removes
  `source_intake_money_classifications`; it does not remove or rewrite the journal, financial
  receipts, CLOSED months or provenance.
- Re-upgrading after a `0060` downgrade creates an empty classification table. Default/manual
  classifications are not reconstructed; a pre-0060 intake returns to
  `classification_missing_legacy_intake` until an exact original is re-saved with a new request
  ID and captured again.
- A `0059` downgrade to `0058` is refused when the source-intake journal is populated. After a
  real upload run it usually is populated, so a `0060 → 0058` downgrade is not a reliable
  recovery route.
- Released migration bytes remain immutable. Do not edit `0060` (or any earlier migration) to
  force a downgrade or to preserve a local table shape.
- The isolated recovery wrapper accepts `same_revision` or one supported unambiguous
  `forward_upgrade`, but only into a **fresh isolated target** that must not already exist and
  must not overlap Stable, Test or any other runtime boundary. Ahead, divergent,
  downgrade-required, ambiguous and unknown graphs are refused before target mutation. It can
  verify a `0058` code/database pair (`same_revision`); it cannot perform a production restore
  or replace the Stable database.
- `uv run alembic downgrade` is not the operational rollback command. Use it only on a
  disposable Test database as described in section 6.

## 5. Production restore status: BLOCKED

The matched `0058` code/database pair cannot currently be restored over the Stable profile with
the accepted procedures. The exact Owner-local paths and backup identity stay outside Git.

**Why the restore is blocked**

- The in-app production restore, `POST /api/backups/{id}/restore`, validates the candidate
  backup's full SQLite schema signature against the live database
  (`services/backups.py::_validate_sqlite_backup`) and refuses
  `Backup schema is incompatible with the live database`. A `0058` backup therefore cannot
  replace a live `0060` database. A same-schema `0060` backup can still be restored within
  1.4.0, but that is not a rollback to v1.3.0. This same-schema restore is the production
  recovery path retained in
  [O1](../OWNER_RUNTIME_OPERATIONS.md#o1-0014-launcher-runtime-profile-safety-77-73-one-way-rule).
- `scripts/recovery-rehearsal.ps1` ([O4](../OWNER_RUNTIME_OPERATIONS.md#o4)) accepts
  `same_revision` or one unambiguous forward upgrade, but restores only into a fresh isolated
  target that must not exist and must not overlap Stable, Test or another runtime boundary. It
  never writes Stable. It can verify that the `0058` recovery point and the published v1.3.0
  checkout form a valid pair; that is not a production restore.
- `scripts/update-stable.ps1` (OPS02) pins and validates the published v1.3.0 code. It does not
  restore a database, and target Prepare/Validate refuses an ahead revision.
- No other repository script or documented operation replaces the Stable database with a
  cross-schema backup. A raw file copy, an in-place Alembic downgrade, a bypassed guard or a
  reused rehearsal target is unsupported ([O4](../OWNER_RUNTIME_OPERATIONS.md#o4)) and must not
  be substituted.

**What may be done now**

1. **Stop the owned runtime.** Use the supported stop operation. Confirm no owned process is
   listening on `8000` and that the Stable directory is no longer mutating.
2. **Preserve the failed state.** Keep the `0060` database, its sidecars and logs, plus the
   pre-upgrade backup and any Test checkpoint. Do not overwrite the only copy of either state.
3. **Verify the selected pre-upgrade backup as evidence.** It must be the `0058` recovery point
   created before the 1.4.0 update, with a successful integrity/foreign-key check (or the
   managed recovery point's verified snapshot readback) and a readable `alembic_version`. If the
   selected artifact is `0059` or `0060`, it is not a v1.3.0 rollback target. Do not publish
   financial values.
4. **Optionally rehearse the pair in isolation, if a matching managed recovery point exists.**
   Run the O4 isolated recovery rehearsal with the `0058` managed recovery point and a clean
   detached v1.3.0 checkout pinned to the published tag. Its `same_revision` acceptance,
   structural checks and readback are the supported proof for the pair. Use a fresh target, do
   not point it at Stable and do not reuse its target. A plain local backup that is not a
   managed recovery point is not accepted by the rehearsal; its SQLite/revision checks remain
   evidence only.
5. **Escalate the production decision.** Either fix forward on `0060` (section 7), the only
   executable production path, or commission a separate production cross-schema restore
   procedure with its own implementation, tests, independent review and explicit
   Owner/Integrator authorization. This plan is not that authorization.

**Post-restore checks (only after an accepted restore procedure exists)**

If a future accepted procedure restores the `0058` database into Stable, complete these checks
before treating the rollback as successful:

1. **Verify the restored database before code preparation.** Confirm `integrity_check` is `ok`,
   `PRAGMA foreign_key_check` is empty, `alembic_version` is
   `0058_broker_money_ownership`, the expected CLOSED months and latest report are present, and
   the `0059`/`0060` tables are absent. Do not publish financial values.
2. **Pin the published v1.3.0 code if the recovery procedure has not already done so.** From the
   trusted control checkout, run OPS02 for the exact published target, with the restored `0058`
   database and a disjoint backup destination:

   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\update-stable.ps1 `
     -StableCheckout <stable-checkout> `
     -TargetVersion 1.3.0 `
     -DatabasePath <verified-0058-production-database> `
     -BackupDirectory <verified-disjoint-backup-directory>
   ```

   OPS02 pins the published tag, verifies the target, runs target Prepare/Validate and stops. It
   does not restore a database, Start the app or downgrade schema. Do not run it against a
   `0060` database and expect it to repair the revision; target Prepare/Validate will refuse the
   ahead revision.
3. **Start separately.** Use the supported Start operation for the restored v1.3.0 checkout.
   Confirm `/api/health` reports `1.3.0`, `alembic current` reports
   `0058_broker_money_ownership`, and representative existing CLOSED/latest reports and their
   provenance are readable. Confirm the `0059`/`0060` tables are still absent.
4. **Record a sanitized receipt.** Include the reason, failure class, candidate and v1.3.0
   identities, observed revisions, backup/recovery-point identifier (local only), restore
   result and the scope of any data loss. Keep all financial values and private paths out of
   GitHub.

If the in-app backup list is used only to identify a pre-upgrade artifact, do not treat a
successful listing as a restore. The in-app restore endpoint itself is refused across schemas,
and a confirmed future restore must be followed by the authoritative readback above. A failed or
ambiguous restore is not success and must not be retried blindly.

## 6. Test-only downgrade drill (not a production rollback)

On a disposable Test/scratch database only, with the assigned Test database selected and the
runtime stopped, the `0060` downgrade can be exercised to confirm the documented behaviour:

```powershell
# From the candidate backend/ on the assigned Test database only.
uv run alembic downgrade 0059_source_intake
uv run alembic current
uv run alembic upgrade head
```

Expected: the first command drops `source_intake_money_classifications`; the journal and
financial tables retain their rows; `current` shows `0059_source_intake`; the re-upgrade creates
an empty classification table and returns to `0060_source_money_classifications`. Run
`PRAGMA integrity_check` and `PRAGMA foreign_key_check` after each step. If the journal is
populated and a downgrade to `0058` is attempted, expect the refusal
`cannot downgrade populated source intake journal`.

This drill proves schema mechanics only. It is not a rollback of Owner data, does not preserve
classification choices and must never be run against Stable or a production database.

## 7. Forward-fix path (only executable production route)

Choose forward fix when the `0059` journal, the `0060` classifications or other post-upgrade
evidence must be retained. In that case:

- keep the `0060` database and stop treating v1.3.0 as the target;
- prepare a new exact candidate with a new additive migration and its own tests;
- obtain independent review and the same Owner/Integrator authorization as any other runtime
  change;
- take a fresh verified backup before the new update;
- do not downgrade, delete the `0060` table, rewrite migration bytes or point v1.3.0 at the
  newer schema.

A forward fix is not a waiver of the failed UAT; record the original failure and its evidence.

## 8. What this plan does not do

- It does not recover source intakes, classifications, overrides or other rows created after
  the selected backup. Those rows are lost from the restored database; original XML statements
  remain with the Owner and may be re-uploaded to a fresh scratch under the selected parser.
- It does not preserve `0060` classification choices across a downgrade or backup restore. There
  is no legacy backfill.
- It does not un-publish a release, rewrite a tag, alter published assets or revert the
  published v1.3.0 identity.
- It does not authorize or perform a Stable update, Start, publication, Apply or Close.
- It does not turn a failed or ambiguous restore into success, and it does not permit a blind
  retry or an improvised raw copy/downgrade.

## 9. Rollback receipt

Record only sanitized evidence:

| Field | Record |
|---|---|
| Trigger | Failure class and short non-reconstructive reason. |
| Candidate | 1.4.0 candidate SHA, observed `0060` revision and runtime profile category. |
| Rollback target | v1.3.0 tag/release commit (public identity), `0058` revision. |
| Recovery artifact | Local-only backup/recovery-point identifier and verification result. |
| Actions | Stop/preserve; restore (BLOCKED unless a separately accepted procedure exists), forward fix, OPS02 pin/Prepare/Validate, Start; PASS/FAIL/NOT TESTED/BLOCKED. |
| Data loss | Categories of post-backup rows not retained (for example, provisional classifications or new source intakes); no values. |
| After state | If an accepted restore or forward fix was completed: health version, observed schema and representative CLOSED/latest readback. For the blocked `0058` restore, state `BLOCKED` and the accepted next action. |
| Follow-up | Forward-fix candidate or renewed UAT plan; Owner/Integrator disposition. |

No sums, balances, account numbers, ISINs, filenames, exact dates, database paths, backup
contents or secrets belong in the receipt.
