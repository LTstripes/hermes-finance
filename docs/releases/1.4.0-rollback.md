## Supported recovery paths and limits

| Path | Supported behavior / explicit limit |
| --- | --- |
| Old code + old data | Preserve published v1.3.0 (`a9c88266fffe26e83688c52fc8f425b04fa14812`) and a verified consistent 0058 point as a matching old pair; structural readback is not permission to replace Stable. |
| O4 detached rehearsal | Use a genuine managed 0058 point, producer/schema/hashes and independent clean exact-release checkout/target. One supported forward 0058→0064 graph, schema and row preservation, readiness. Never overwrite Test/Stable. |
| 0064 same-schema restore | Supported stock in-app restore requires matching live schema signature; a valid 0064 backup cannot return the app/database to v1.3.0/0058. |
| Bounded checkpoint forward recovery | [O4 forward-recovery](../OWNER_RUNTIME_OPERATIONS.md#o4-forward-recovery) stays on the exact new published/prepared code; qualifies frozen checkpoint/plan, native custody and incident fence, then explicit recover/resume/finish. Requires separate Owner-authorized RPO/cutoff and is **not** old-code rollback. |
| Fix forward | After a post-upgrade defect, an independently accepted corrective release can preserve data at 0064 or later. Time-to-fix and availability are an Owner risk decision, not an automatic safe fallback. |

An OPS02 `.sqlite3` backup is **not** a managed recovery point and cannot be
relabeled with invented producer SHA, protection attestation or manifest.

## Hard restriction after production migration

**No stock cross-schema Stable rollback.** The in-app restore rejects a 0058
backup against a 0064 database. OPS02 rejects an older target version, even
before migration. v1.3.0 must **never** open a 0059–0064 database. Populated
0063 audit or 0064 `actual_fact_origin` refuses Alembic downgrade before DDL;
0060 classifications, 0061 links and 0062 crosswalk also have loss boundaries.
Deleting audits/origins, downgrading, ref-reset, raw SQLite replacement or
switching to Test DB are not accepted recovery procedures.

A checkpoint forward recovery may lose transactions newer than the chosen
managed point. Source integrity/hashes do not imply a zero-loss RPO. Owner and
Integrator must explicitly accept the bounded checkpoint and potential outage
or reject production Start; do not infer consent from earlier Test O4 approval.
