# 1.4.0 recovery disposition — 0058 → 0062

Preparation under [#940](https://github.com/LTstripes/hermes-finance/issues/940#issuecomment-6369675756).
This supersedes the 0060 snapshot and its unsafe OPS02 repin suggestion. It is a decision
aid under [O3](../OWNER_RUNTIME_OPERATIONS.md#o3)/[O4](../OWNER_RUNTIME_OPERATIONS.md#o4),
not authorization to replace production data.

## Supported routes

| Route | Current support and limit |
| --- | --- |
| Preserve/verify old pair | Keep published v1.3.0 `a9c88266fffe26e83688c52fc8f425b04fa14812` with consistent 0058 backup. Read-only integrity/FK/schema prove readability, not production restore. |
| O4 isolated rehearsal | Valid managed point, clean detached exact-SHA code, explicit inventory/protection attestation, fresh disjoint non-Stable/non-Test target. Accepts same_revision or one unambiguous forward_upgrade; failed/ambiguous targets are never reused. |
| Same-schema in-app restore | Backup must match live schema signature. A compatible 0062 backup may recover 0062 through supported confirmation/readback; this is not return to v1.3.0. |
| Fix forward | Accepted corrective candidate retains migrated data. Sufficiency of this operational risk is an explicit Owner/Integrator decision. |
| Bounded checkpoint forward recovery | [O4 procedure](../OWNER_RUNTIME_OPERATIONS.md#o4-forward-recovery) stages an authentic managed 0058 point, forward-migrates it with the selected future release and installs under pre-writer fence/native custody with incident retained. Requires independent operational acceptance and explicit checkpoint/RPO authority; it never repins old code or downgrades. |

An OPS02 `.sqlite3` backup is not automatically a managed recovery point. The O4 wrapper
requires manifest/protection/hashes/producer identity. Do not fabricate a manifest or wrap
an old snapshot with an invented producing SHA.

## Finite blocker before production Start

**Stock cross-schema rollback is absent.** API restore refuses 0058 over 0062:
`Backup schema is incompatible with the live database`. OPS02 refuses an older target
version before the update, including after a 1.4.0 code pin while the DB is still 0058.
An unchanged DB does not waive that guard. O4 never overwrites Stable.

No command here restores the old pair over production. The bounded forward route
keeps the selected future code and requires the O4 predicates; it does not waive
publication/local authority or the limits after OS/storage failure. Raw-copy replacement, Alembic
downgrade, ref reset, guard bypass, Test transfer or rebinding is unsupported. v1.3.0 code
must never open 0059–0062.

Before production Start, Integrator must obtain a separately accepted bounded production
recovery procedure (implementation/tests/independent review/local authority), or explicitly
settle with Owner the residual outage/recovery risk and forward-fix disposition. Worker does
not select that policy. This task does not launch a broad recovery redesign. Publication
through #124 follows Integrator acceptance of this preparation.

## Concrete preparation

1. Verify Stable checkout/prepared HEAD, actual process/listener owner, effective DB selector,
   canonical production binding and disjoint backup destination. Inspect DB with `mode=ro`
   and `query_only`; never invoke migration-capable startup for diagnosis.
2. Record revision, integrity/FK and private structural/logical evidence for CLOSED/history/
   provenance. Keep local paths, fingerprints and row contents out of GitHub.
3. Preserve available verified old backups/code. At actual update, make and verify a fresh
   backup-first OPS02 snapshot; previous backups do not replace it.
4. Test direct and hop-by-hop 0058→0059→0060→0061→0062 preservation on synthetic data;
   verify old online backup/readback and a fresh synthetic forward-recovery target.
5. A full O4 rehearsal additionally needs a valid managed point and free authorized runtime
   slot. Bind producer/source revisions, selected recovery SHA/heads and relationship. If
   prerequisites are missing, report NOT RUN with the finite reason; isolated proof is not
   production restore or Owner numerical UAT.
6. On failure, preserve DB/sidecars/logs and pre-upgrade backup; stop only the owned process.
   Diagnose the exact failed phase. An ambiguous result blocks blind replay and target reuse.

0059 refuses downgrade of a populated journal; 0060 drops classifications; 0061 drops link
fields; 0062 drops mappings. Re-upgrade does not restore choices/mappings. These loss
boundaries justify backups, not a production downgrade recipe. Released migrations stay immutable.
