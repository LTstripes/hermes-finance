# 1.4.0 monthly returns — Owner Test-run checklist

> **Status:** preparation aid for an unpublished candidate. This is not a release, UAT
> acceptance, financial result or authorization to write production data. Use it only on a
> separate Test or disposable scratch Preview runtime, never on Stable.

`1.4.0` is the draft release identity. The candidate checkout still reports the existing
application version (`1.3.0`) until a separate version bump; do not expect the UI or
`/api/health` to say `1.4.0` during this run.

This checklist validates the provisional monthly source-return slice described in
[the 1.4.0 draft notes](../release-notes-1.4.0.md) on an exact candidate. It covers the domain
monthly chain (#911), the source monthly API and migration `0060` (#913), per-instrument returns
(#915) and the v2 «Доходность по месяцам» page (#917). The controlling procedures remain
[the real Owner UAT procedure](../DEVELOPMENT.md#d4-ui_v2_owner_uat-5-assignment-and-backup-first),
[Test/scratch preparation](../OWNER_RUNTIME_OPERATIONS.md#o2) and
[backup, restore and ambiguous results](../OWNER_RUNTIME_OPERATIONS.md#o4).

## 1. Scope, authority and stop conditions

- [ ] The Integrator/Owner assigned the exact 40-character candidate SHA, trusted control
      checkout, separate Preview/Test checkout, assigned Test data directory/database, Stable
      checkout/data/database and a representative real-statement source. No path or value is
      invented by the tester.
- [ ] The runtime is a separate Test/scratch Preview. Stable is stopped or otherwise not the
      running profile; only one profile owns port `8000`.
- [ ] The tester is authorized to read the selected private statements and the assigned Test
      database under D1. Credentials stay excluded; reads do not authorize production writes,
      runtime changes or publication.
- [ ] No production database, Stable data directory, live `finance.db` or unassigned SQLite
      sidecar is opened, copied, migrated or repaired by this run.
- [ ] The run stops immediately on any of: Stable mutation, wrong database identity, unknown or
      ahead schema, migration failure, integrity/foreign-key failure, an unexpected financial
      Apply/Close/receipt write, a secret in output, or an ambiguous restore. Preserve the
      evidence and use the [rollback plan](1.4.0-rollback.md); do not blind-retry.

## 2. Backup before anything is copied or started

- [ ] Create and verify a consistent backup of the source database with the supported Owner
      backup/recovery procedure. Do not substitute a raw copy of a live locked database.
- [ ] Verify the backup is readable SQLite (`integrity_check` is `ok`, `alembic_version` is
      readable), or use the managed recovery point's verified snapshot readback, and record the
      selected recovery point/manifest identity locally.
- [ ] Create a second checkpoint backup of the assigned Test database immediately before the
      first candidate start. This is the Test-local recovery point for repeated runs.
- [ ] Record the pre-start revision. Expected cases:
      - an existing source-intake scratch is at `0059_source_intake`; the candidate should move
        it to `0060_source_money_classifications`;
      - a copy of the published v1.3.0 database is at `0058_broker_money_ownership`; the
        candidate should move it through `0059` to `0060`;
      - a repeated run from the Test checkpoint is already at
        `0060_source_money_classifications`; confirm it is the same assigned Test database and
        candidate, and expect no migration.
      Any other starting revision is a gate: stop and diagnose before starting.
- [ ] Keep both the pre-upgrade backup and the Test checkpoint backup until the run and any
      rollback decision are complete. Backup identifiers and paths stay Owner-local.

## 3. Migration check: 0059 → 0060 (and 0058 → 0060)

- [ ] Prepare the exact candidate with the supported OPS03/Prepare/Validate route. Confirm the
      prepared checkout `HEAD` equals the assigned candidate SHA and that startup selects only
      the assigned Test database.
- [ ] Before Start, from the candidate `backend/` with the assigned Test database selected,
      run the read-only Alembic current check and record the exact revision:
      `uv run alembic current`.
- [ ] Start through the supported operation. Do not start the candidate against Stable, a
      development database or an unassigned path.
- [ ] After Start, re-run `uv run alembic current` and record the result. It must be
      `0060_source_money_classifications` (head). Capture the observed revision, not an assumed
      one.
- [ ] Confirm the new `source_intake_money_classifications` table exists; on the first migration
      from `0059` it is empty. Confirm existing source-intake journal and financial tables are
      still readable, with no integrity or foreign-key failure. On a repeated run, record only
      that prior rows exist, not their contents.
- [ ] Confirm `/api/health` reports the version from the prepared checkout and the UI loads.
      The draft still reports `1.3.0`; health/version alone is not proof of data continuity.
      Also open representative existing CLOSED months and the latest report, and confirm they are
      unchanged.
- [ ] Confirm the candidate did **not** backfill classifications for pre-0060 intakes. When
      their Money rows are used, expect `classification_missing_legacy_intake` rather than a
      guessed or zero classification.
- [ ] If the pre-start revision was `0058`, repeat the revision/table checks for the
      `0058 → 0059 → 0060` path. Both migrations are additive; any unexpected table loss,
      revision jump or refusal is a stop condition.

Useful read-only evidence for the run receipt: pre/post revision names, table presence,
integrity/foreign-key result, health version and candidate SHA. Do not record private values.

## 4. Multi-file upload

- [ ] Open `/v2/capital/monthly-returns` (or follow «Доходность по месяцам» from the v2
      «Доходность» page).
- [ ] Select multiple real monthly XML statements in «Добавить несколько файлов» and upload them
      in one batch. Use statements the Owner has authorized for this Test run; do not add
      invented or synthetic rows to a real database.
- [ ] Each file moves through its own state independently: «Сохраняем» → «Сохранен» or
      «Не сохранен». One file's save error must not reject the successful files in the batch.
- [ ] For each saved file, the authoritative readback reports the saved observation count and
      either no gaps or the actual exceptions. A save is not reported as a readback failure.
- [ ] If readback fails, the row shows «Сохранен · не удалось прочитать» and offers
      «Повторить чтение <file>». Retry reads the same intake; it must not upload the file again.
- [ ] Re-upload the same original in a new batch. The duplicate guard must not create duplicate
      journal occurrences or duplicate classifications. An acknowledged same-request replay
      remains read-only; an exact original re-save with a new request ID may capture missing
      legacy rows.
- [ ] The «Счёт в выписке» selector lists the native source account(s) from the saved intakes.
      Select the account intended for this run and record that a selection was made, not the
      account value.

## 5. Expected flags, gaps and null behaviour

Check the badges and the «Пробелы и перекрытия источников» list against what the supplied
statements can actually support. A clean row is not proof of completeness.

| Observed flag/badge | Meaning in this slice | Expected when |
|---|---|---|
| «приблизительно» / `approximate=true` | The monthly/period estimate is approximate, or the instrument uses a bond valuation or assumed income. | Always on monthly and period source rows; bonds; any row using assumed income. A stock month may be non-approximate only when no gaps or assumptions apply. |
| «частичные данные» / `partial` | A period endpoint is missing, a monthly instrument total is withheld, or an all-time instrument total is partial. | A missing monthly boundary; an instrument month with no available total; an instrument all-time row with partial/missing months. |
| «доходы неполные» / `income_complete=false` | Some covered income rows are unknown, unattributed, invalid, legacy-unclassified, non-RUB or structurally uncovered. | The affected instrument row. Monthly source rows do not carry this badge; their income gaps appear in the flags/gaps list. Observed matching income may still be shown; no matching income is `null`, not zero. |
| «потоки с допущениями» / `assumptions_used` | At least one included external flow uses a default rule (`assumed`). | Deposits/withdrawals captured only by default classification. |
| «купоны/дивиденды с допущениями» / `income_assumptions_used` | At least one included coupon/dividend uses a default rule. | Income captured only by default classification. |
| «нет границы месяца» / `missing_endpoint` | The opening or closing native EOD total is unavailable. | A statement gap, partial month or missing outer boundary. Growth and rate for the affected interval stay `null`; known contributions and withdrawals remain available. |
| «неизвестный поток» / `unknown_flow` | An included Money row cannot be classified or validated, so the flow schedule is unknown. | Unknown/unrecognized/invalid RUB Money, non-RUB Money (`currency_unsupported`), or an unreadable/ambiguous original covering the month. Affected flow-dependent metrics are `null`. |
| «расхождение границ» / `seam_mismatch` | Consecutive source boundaries disagree. | Overlapping or different statements with different opening/closing totals. Both operands are retained; nothing is averaged or replaced. |
| «месяц отсутствует» / `missing_month` | No usable whole-month source coverage. | A month with no saved statement coverage. It is missing, not a zero return. |
| «источник покрывает месяц частично» / `partial_month_source` | The statement covers only part of the month. | Partial-month source files. The affected month stays partial; do not infer the rest. |
| «доход не отнесён» / `unattributed_income` | Coupon/dividend income could not be matched to an instrument. | Ambiguous or missing ISIN/registration/name attribution. The amount remains visible as an income observation but is not assigned to an instrument. |
| «повтор потока в перекрывающихся выписках учтён один раз» / `overlap_flow_deduplicated` | The same external flow was present in overlapping statements. | Overlapping statements covering the same flow. Confirm it is counted once, not twice. |
| `currency_unsupported` | Non-RUB Money makes the affected month's flows unknown. | Any non-RUB Money row. Independent RUB-only months may remain available. |
| `classification_missing_legacy_intake` | The intake predates migration 0060 and has no persisted classifications. | Pre-0060 intakes. Reads do not backfill or treat missing rows as zero. |
| Instrument flags such as `trade_identity_unresolved`, `trade_nkd_basis_unknown`, `trade_nkd_basis_conflict`, `trade_missing_settlement`, `currency_unsupported` | The affected trade, NKD basis, settlement or currency component is unresolved. | Withhold the affected cost/total/rate; do not turn unknown into zero. |
| `bond_valuation_basis_unknown` | The bond row uses reported values without resolving clean/dirty or accrued-interest basis. This is an approximation disclosure, not a blocker. | Always on bond rows. Keep the numbers with `approximate=true`; do not present them as an exact bond total return. |
| Status «полные данные» | The UI found no approximate/partial/income-incomplete marker on that row. | Only when the API also reports no such marker. This is a presentation state, not financial completeness or Close authority. |

Additional checks:

- [ ] The «Потоки по правилам по умолчанию (допущения)» list shows default-classified
      flows with their included/excluded state. A default is visible as an assumption; it is
      not silently promoted to a confirmed financial fact.
- [ ] `null` and zero are visibly different. A missing endpoint-derived growth or rate, unknown
      flow, unknown income, missing month or withheld NKD basis displays as unavailable, not as a
      zero amount or 0 %.
- [ ] A monthly income subtotal of zero must be read with the flags: an incomplete month can
      show only observed income (possibly zero) while its gap is disclosed separately. Do not
      treat a zero subtotal as proof that no income existed.
- [ ] `RUR` is treated as `RUB`; no native source row is rewritten by the reader.
- [ ] A long report that supplies only its outer EOD boundaries shows a `partial_segment` with
      period totals and no monthly chain. This is expected, not a missing-data bug.

## 6. Contributions vs growth sanity

For one month whose statement values are visible locally, use the opening/closing totals from
the statement or the read-only API and check the arithmetic without publishing the values:

- [ ] `growth = closing total − opening total − contributions + withdrawals`.
- [ ] Contributions and withdrawals contain only classified external flows. A deposit or
      withdrawal appears once; a coupon or dividend is shown as income and is not added again as
      an investor flow.
- [ ] A transfer between the Owner's own accounts, an internal transfer, an unknown Money row or
      an invalid row does not silently become an external contribution or withdrawal.
- [ ] Closing-day external flows have zero Modified Dietz weight; verify the displayed monthly
      rate is plausible for that timing rather than assuming a full-month weight.
- [ ] Negative growth and a negative monthly rate are possible and must not be clamped to zero.
      A zero rate is accepted only when the operands are known and the arithmetic supports it.
- [ ] If any month in the chain is missing or has an unknown flow, the chained return is `null`.
      Period growth or XIRR may still be shown from the outer endpoints and known flows; that is
      an intentional independent result, not a contradiction.
- [ ] A nonpositive Modified Dietz denominator withholds the rate while preserving known growth.
      XIRR may be unavailable for solver reasons; it is not zero.
- [ ] The all-time `XIRR, годовых` and `XIRR за период` figures are consistent with each other
      for the displayed outer period, and the chained Modified Dietz is labelled approximate
      «≈TWRR», not exact TWRR.

## 7. Per-instrument price, coupons/dividends and NKD

- [ ] The instrument table shows «Изменение цены», «Купоны», «Дивиденды», «Итого»,
      «Доходность» and the quality/flags column for each instrument and its months.
- [ ] `Итого` is price effect plus income for the month. Coupons and dividends are not included
      twice and are not treated as external contributions.
- [ ] All-time monetary fields are sums of available monthly components. The all-time
      percentage is `null` by design; it is not a holding-period, chained or annualized rate.
- [ ] `available_months`, `missing_months` and `partial_months` agree with the visible month
      rows. A missing month is not a zero-return month.
- [ ] For at least one bond buy and one bond sell, verify NKD is counted once. The page has no
      separate NKD column; check the affected price-effect/total components against the
      statement and the documented basis flags. An accepted proof or a unique per-row MyBroker
      inference may resolve the basis. An inconclusive inference (both or neither match)
      preserves a valid accepted proof; the affected numbers are withheld only when neither a
      proof nor a unique inference resolves the basis, or when a decidable inference conflicts
      with the proof (`trade_nkd_basis_unknown` / `trade_nkd_basis_conflict`). Do not infer the
      basis from a current price alone. If the selected history has no bond trade, mark this
      NOT TESTED rather than manufacturing one.
- [ ] For a stock, omitted NKD is inapplicable zero, not an unknown bond NKD. A stock month is
      approximate only when another gap or assumed income applies.
- [ ] Bond rows disclose `approximate=true` and `bond_valuation_basis_unknown`; reported values
      do not resolve clean/dirty or accrued interest. Do not present them as exact bond total
      return.
- [ ] Income is attributed by whole ISIN or an explicit saved registration alias before whole
      saved names. An unattributed coupon/dividend stays unassigned and visible; it is not
      silently dropped or assigned to a guessed instrument.
- [ ] Fees and taxes are not presented as a net-of-tax result. This view makes no tax or
      cost-basis claim.

## 8. Reconcile against the broker statement

- [ ] Choose one month and compare the page's contributions, withdrawals, growth, coupon/dividend
      income and per-instrument components with the Owner's broker statement. Where opening or
      closing totals are needed, read them from the statement or the read-only API, not by editing
      data. Do this locally; do not publish values.
- [ ] Every difference is explainable by a visible flag or documented limitation: missing/partial
      month, seam mismatch, unknown or non-RUB flow, default-assumed classification, unattributed
      income, bond valuation basis, NKD basis, missing settlement, or unsupported section.
- [ ] If a difference cannot be explained, record FAIL or NOT TESTED with the flag category, not
      an invented zero or a forced match. Do not edit Hermes data merely to reproduce the broker
      number.
- [ ] Confirm viewing, account selection and readback retry remain read-only: no Apply, Close,
      Reopen, receipt, metadata promotion or financial write is triggered by them. The explicit
      upload is the only expected write, and it creates source-intake journal/classification rows.
- [ ] Confirm no broker communication or provider call is required or performed for this check.

## 9. Owner/Integrator receipt

Record only sanitized evidence. The receipt must be sufficient to reproduce the check without
reconstructing private values.

| Field | Record |
|---|---|
| Candidate | Full 40-character SHA; branch and prepared checkout identity. |
| Runtime | Test/scratch profile name (generic); confirms Stable was not the running profile. |
| Schema | Observed pre-start and post-start revision names; confirms `0060`; starting path `0059→0060` or `0058→0060`. |
| Backup | Local-only backup/recovery-point identifier and verification result; do not include paths or contents. |
| Upload | Number and categories of files (for example, monthly source statements), batch outcomes and readback outcomes; no filenames, accounts, dates or values. |
| Steps | PASS / FAIL / NOT TESTED for each section above, with a short non-reconstructive observation. |
| Flags | Observed flag/badge codes and whether each matched the expected condition. No amounts. |
| Null/zero | Confirmation that unavailable values (missing endpoint-derived growth/rate, unknown flows, incomplete income) stayed unavailable rather than zero. |
| Reconciliation | PASS/FAIL/NOT TESTED and the flag category for each explained difference; no figures. |
| Limits | Synthetic-tested status, approximate Modified Dietz/XIRR, no Owner-real numerical acceptance, no financial authority. |
| Disposition | Owner/Integrator role (no private contact data), date, and whether the candidate is accepted for the next gate; release is not implied. |

Do **not** put any of the following in GitHub, a PR, an issue comment or a screenshot: sums,
balances, account numbers, ISINs or instrument names, statement filenames, exact transaction or
coverage dates, database paths, backup contents, credentials or private screenshots. A count,
category, PASS/FAIL state, revision name and candidate SHA are sufficient.

## 10. Exit criteria

- [ ] Every mandatory step above is PASS, or a NOT TESTED/FAIL is explicitly accepted by the
      Integrator with its scope and limitation recorded.
- [ ] Return reads remain read-only; the only writes are the authorized source-intake
      journal/classification capture from the upload. No financial Apply/Close/receipt or
      metadata promotion occurred, and no financial authority was created.
- [ ] The Test database and backups are preserved until the disposition is recorded.
- [ ] The receipt states that the result is **not** financial acceptance, not a Close/Apply
      authorization, not publication and not a Stable update.
- [ ] If any mandatory step fails, use the [1.4.0 rollback plan](1.4.0-rollback.md) and do not
      request a release-control action.
