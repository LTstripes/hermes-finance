## 0. Назначение и границы релиза

`0.3.0` — большой UI/UX pass без пересмотра принятых финансовых формул и privacy-архитектуры. Цель — превратить технически корректный MVP-интерфейс в спокойный ежедневный инструмент управления личными финансами: меньше постоянного текста и служебных деталей, сильнее визуальная иерархия, понятнее workflow месяца, явное различие между фактом, прогнозом и целью, отдельная аналитика динамики состава капитала.

Продуктовая цель интерфейса: **calm financial cockpit** — важные цифры и следующее действие видны сразу; методология, диагностика и редко нужные детали доступны по запросу, но не конкурируют с основным содержанием.

### В scope

- информационная архитектура Dashboard / Analytics / Months / Month workspace / Goals;
- action hierarchy: primary / secondary / overflow / destructive;
- shared UI primitives, spacing, typography и responsive rules;
- sticky lifecycle header для отчётного месяца;
- разделение длинного Month editor на кликабельные рабочие секции;
- review/close flow вместо большого closeout-блока внизу страницы;
- Fact / Forecast / Goal visual semantics;
- tooltip / popover / details вместо постоянных методологических текстов;
- единые warning / empty / locked / error / success states;
- перенос технических runtime/status деталей в diagnostics;
- отдельный Analytics screen с историей состава ликвидных активов по классам;
- минимально необходимое расширение read-only analytics API для этой истории;
- desktop responsive target, включая `1366×768` и уменьшенное окно приложения;
- visual/smoke verification на локальном Windows runtime.

### Не в scope

- cloud, auth, telemetry, VPS, multi-user;
- изменение финансовых формул, tax semantics, goal-current-value semantics или источников истины;
- автоматическое заполнение будущего календаря выплат (`R02-26` остаётся DEFERRED);
- trading/portfolio execution;
- mobile-first redesign;
- крупная смена цветовой темы/бренда;
- новый frontend framework/design-system dependency без отдельной необходимости.

### Неподвижные инварианты

- приложение остаётся local-only и слушает `127.0.0.1:8000`;
- money/rates/rounding и прочие финансовые инварианты из `MASTER_SPEC`, ADR и `AGENTS.md` не меняются;
- frontend не начинает самостоятельно пересчитывать финансовые значения, которые являются backend source of truth;
- `Actual`, `Forecast` и `Goal` не смешиваются семантически и визуально;
- closed month остаётся immutable до explicit reopen;
- private seed, локальная БД и реальные персональные финансовые данные не попадают в Git, fixtures, screenshots CI или логи.

## 1. UX contract 0.3

### 1.1 Основной принцип

По умолчанию интерфейс показывает:

1. результат;
2. контекст, необходимый для правильной интерпретации результата;
3. одно главное следующее действие.

Методология, API/backend terminology, диагностические поля и редкие действия не должны постоянно занимать первый уровень интерфейса.

### 1.2 Action hierarchy

- В одной визуальной области должна быть не более одной явной primary action.
- Secondary actions остаются видимыми только когда используются регулярно.
- Редкие действия уходят в `…` / overflow menu.
- Destructive actions по умолчанию не конкурируют с primary; они живут в overflow/menu/dialog и требуют confirm там, где действие необратимо.
- `Обновить` не является визуальной primary action, если данные обычно загружаются автоматически.
- Calculated/read-only value не маскируется под editable input без необходимости.

### 1.3 Progressive disclosure

Три уровня пояснений:

- **всегда видно** — только информация, без которой пользователь может неверно понять цифру или выполнить опасное действие;
- **`ⓘ` tooltip/popover** — короткое объяснение метрики, неполного окна, причины недоступного прогноза, lock-state;
- **`Подробнее` / `<details>`** — длинная методология, composition rules, технические подробности.

User-facing основной поток не должен содержать ссылки вида `MASTER_SPEC §...`, endpoint names (`/api/...`), storage names (`income_type=...`) и слова `backend` как объяснение поведения. Такие детали допустимы только в Diagnostics/technical details.

### 1.4 Fact / Forecast / Goal

Единый визуальный язык по всему приложению:

- **Fact / Факт** — solid и самый контрастный data series/state;
- **Forecast / Прогноз** — визуально вторичный, dashed/amber или эквивалентный стиль, никогда не выглядит как уже полученный результат;
- **Goal / Цель** — reference/target marker, не data series факта;
- **incomplete history** — muted indicator + help, а не большой warning, если действие пользователя не требуется.

Цель passive income показывает current value только по принятому контракту 0.2: rolling average фактического net passive income по CLOSED месяцам. Forecast остаётся отдельной метрикой.

### 1.5 State model

| State | Presentation |
|---|---|
| Error, операция невозможна | persistent red alert + recovery action, если есть |
| Warning, требуется решение пользователя | persistent amber alert |
| Неполные данные, но интерфейс корректен | muted badge / `ⓘ` / concise note |
| Empty | короткое объяснение + максимум один основной CTA |
| Closed / locked | статус в sticky header + read-only presentation; длинное постоянное объяснение не требуется |
| Success | короткий transient feedback/toast там, где это возможно |
| Technical diagnostics | Settings → Diagnostics / раскрываемые technical details |

### 1.6 Responsive contract

Минимальная обязательная owner-visible матрица:

- широкий desktop;
- `1366×768`;
- уменьшенное desktop window примерно `1024px` по ширине;
- fallback до текущего минимального supported viewport без налезания controls на данные.

Правила:

- таблицы сначала теряют второстепенные колонки/actions, и только затем используют horizontal scroll как fallback;
- row actions → одна основная action + overflow;
- двухколоночные формы → одна колонка на узком viewport;
- Month workspace section navigation может перейти из вертикальной навигации в горизонтальные tabs/select;
- sticky month lifecycle controls должны оставаться доступны без перекрытия контента.

## 2. Новая информационная архитектура

### Sidebar

```text
ОБЗОР
  Дашборд
  Аналитика

УЧЁТ
  Месяцы
  Счета и инструменты

ПЛАНИРОВАНИЕ
  Цели

СИСТЕМА
  Экспорт и бэкапы
  Настройки
```

`Настройки` получают отдельный раздел/подраздел Diagnostics для runtime/backend status, version/local bind и прочей служебной информации.

### Dashboard

Dashboard отвечает только на вопрос «что сейчас происходит с моими финансами?».

Верхний уровень — до четырёх смысловых KPI-блоков:

1. **Капитал** — текущее значение + изменение за выбранный месяц внутри одной карточки;
2. **Пассивный доход** — Fact + Forecast + Goal в одном сравнительном блоке;
3. **Основная цель** — progress + remaining; forecast date только если она реально projectable;
4. **Покрытие обязательных расходов** — компактная текущая метрика.

На Dashboard не должны оставаться отдельные служебные блоки Backend Status, техническая сводка выбранного месяца и полная таблица отчётных месяцев. Подробный результат по классам/счетам и распределение активов переходят в Analytics.

Допустимо оставить два основных overview-графика: общая динамика капитала и фактический пассивный доход с reference lines Forecast/Goal.

### Analytics

Новый route `/analytics`.

Первый обязательный экран 0.3 — **Капитал**:

- stacked area по историческим CLOSED месяцам;
- классы: cash, deposits, stocks, bonds, gold/other — в соответствии с существующим accepted asset-allocation contract;
- переключатель `Сумма ₽ / Доля %`;
- tooltip месяца показывает сумму каждого класса;
- общий net liquid capital показывается отдельно и не должен визуально обещать равенство stack total, если принятый backend contract учитывает обязательства вне asset-allocation stack;
- отсутствие закрытого месяца не интерполируется;
- текущий snapshot allocation и подробный investment result по классам/счетам живут в Analytics, а не на первом уровне Dashboard.

### Months

Основной экран — список периодов и одна явная action `Создать следующий месяц`.

Из таблицы/списка убрать постоянный шум:

- `Источник` не является обязательной колонкой первого уровня;
- видимая row action — `Открыть`;
- `Клонировать`, `Удалить черновик` и редкие действия → overflow;
- ручное создание произвольного периода → dialog/modal, а не постоянно занятая правая колонка.

### Month workspace

`MonthDetailPage` перестаёт быть одной длинной страницей из всех секций.

Верхний sticky lifecycle header:

```text
Июль 2026 · Черновик    Капитал …   Пассивный доход …   ⚠ N
                                 [Сохранить] [Проверить и закрыть]
```

Основные кликабельные секции:

- Общие данные
- Доходы
- Активы
- Позиции
- Выплаты
- Бюджет
- Долги / недвижимость
- ИИС (если month-level данные действительно нужны здесь после декомпозиции)
- Заметка месяца
- Проверка

Одновременно на первом уровне показывается одна рабочая секция, но пользователь может перейти в любую секцию напрямую. `Назад / Далее` допустимы как удобство, но это не жёсткий wizard.

В sticky header/section nav должен быть понятен status заполнения/ошибок секции без ложного требования «заполнить всё», если поле или секция optional.

### Close / reopen lifecycle

`Закрытие месяца` больше не является большим контейнером для несвязанных функций внизу страницы.

`Проверить и закрыть` открывает focused review flow:

- ключевые KPI месяца;
- blockers и action-required warnings;
- concise checklist readiness;
- основная цель как информационный summary при наличии;
- primary `Закрыть месяц`.

Для CLOSED месяца sticky header предоставляет secondary action `Открыть для редактирования` с существующим explicit reopen contract.

Из текущего closeout-компонента должны быть концептуально вынесены:

- IIS profile/contributions/benefits — в релевантный account/IIS context;
- legacy Main Goal fragment — удалить; source of truth уже полноценный Goals API;
- comments — представить как `Заметка месяца`, а не часть closeout;
- system/API explanatory text — удалить с обычного первого уровня.

### Goals

Небольшое число целей отображается карточками, а не широкой таблицей.

Главная цель показывает:

- имя/status badges;
- `current / target`;
- progress bar;
- remaining;
- achievement date только при projectable forecast;
- `ⓘ`/details для reason/warnings/calculation mode;
- одна видимая `Изменить`, остальные редкие actions → overflow.

Неактивные цели по умолчанию скрыты в компактном `Архив целей (N)`.

## 3. Роли: Лера / Hermes / Codex

### Product/contract ownership

**Лера (GPT-5.6 Sol / Chat)**:

- product/UX direction;
- информационная архитектура;

- решение неоднозначностей до implementation;

- acceptance визуальной/семантической части перед переходом к следующему крупному UX-блоку.

### Hermes

Предпочтителен, когда задача требует:

- локального Windows runtime;
- запуска реального приложения на `127.0.0.1:8000`;
- visual/smoke проверки в небольшом desktop viewport;
- проверки interaction flow close/reopen/editor;
- production probe, cleanup процесса/порта и release smoke;
- реализации, где быстрое локальное «посмотреть глазами → поправить → снова проверить» важнее чисто repo-level refactor.

При Hermes route точная модель выбирается по `MODEL_ROUTING.md`; обычный UI по закрытому контракту — Luna High, финансовая семантика — не ниже соответствующего gate.

### Codex

Предпочтителен для хорошо изолированных repo-level задач:

- component/refactor work с чётким acceptance;
- React/TypeScript implementation и tests без необходимости private/local data;
- отдельный backend DTO/query endpoint по уже закрытому контракту;
- механический cleanup technical copy/states;
- scoped CSS/layout changes, если visual acceptance затем делает Hermes/Лера.

Codex не получает разрешение самостоятельно менять финансовую семантику, расширять scope, push/merge/release или принимать собственную работу финально.

### Fair A/B comparison rule

Если task-card отмечена `A/B candidate`, Hermes и Codex могут получить **одинаковый prompt и одинаковый baseline commit** в отдельных branch/worktree/session. До выбора победившего варианта оба работают без push/merge в remote main. Сравнение делается по diff, tests, UX, объёму лишних изменений и local visual smoke. После выбора применяется только один вариант либо осознанно собранный reviewed diff.

## 4. Общий Definition of Done 0.3

Для каждой `R03-*` task-card:

1. прочитаны точная task-card, `AGENTS.md`, `MODEL_ROUTING.md`, связанные MASTER_SPEC/ADR;
2. task не меняет финансовую семантику без отдельного contract task;
3. до изменения дан план 3–7 шагов;
4. изменён только заявленный scope;
5. targeted tests проходят; broader frontend/backend checks выполняются пропорционально риску;
6. UI task проверен минимум на normal desktop и `1366×768`; задачи Month/Actions дополнительно на уменьшенном desktop window;
7. controls не перекрывают data/text и не создают horizontal action pile-up;
8. новые user-facing copy не содержит технической терминологии без необходимости;
9. private data/DB/backups/exports/screenshots с реальными значениями не попали в Git;
10. принимающий reviewer смотрит фактический diff, а не только summary worker;
11. next task не стартует автоматически без явного назначения владельца согласно `AGENTS.md`.
