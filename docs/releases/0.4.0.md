## 0. Назначение и границы релиза

`0.4.0` добавляет первую внешнюю read-only интеграцию: обновление рыночных котировок поддерживаемых инструментов через MOEX по явному действию владельца.

Релиз сознательно ограничен котировками и provenance. Он не должен превращаться в торговую систему, фонового синхронизатора или универсальный market-data layer.

### В scope

- идентификация поддерживаемых инструментов для MOEX;
- явное сопоставление локального инструмента с внешним market identity;
- получение актуальной доступной котировки только по явному запросу пользователя;
- preview `текущее значение → предложенное значение` до применения;
- дата котировки и источник;
- partial success / unavailable / stale / ambiguous mapping states;
- явное исключение инструмента из автообновления;
- сохранение ручной цены для замороженных, иностранных или неподдерживаемых активов;
- explicit apply выбранных обновлений;
- локальный audit/provenance без фоновой телеметрии;
- tests + Windows/CI release gate.

### Не в scope

- фоновые запросы/cron/daemon refresh;
- торговые операции;
- broker API / banking API;
- автоматическое изменение закрытых месяцев;
- автоматическое создание expected cash flows;
- купонный/дивидендный календарь (планируется отдельным `0.5.0`);
- импорт PDF Альфа;
- cloud/auth/telemetry/VPS/multi-user;
- изменение финансовых формул.

### Неподвижные инварианты

- приложение остаётся local-only и слушает только `127.0.0.1:8000`;
- внешний источник используется read-only;
- никаких сетевых запросов без явного действия пользователя;
- полученная извне цена никогда не применяется молча;
- frontend не становится source of truth финансовых вычислений;
- closed month immutable до explicit reopen;
- manual price остаётся поддерживаемым workflow;
- private DB/seed/exports/backups/реальные финансовые payload не попадают в Git/CI/logs.

## 1. Branching и параллельная поддержка

До выпуска `0.4.0` существуют две независимые линии.

### `main` — стабильная линия `0.3.x`

- содержит latest accepted/releasable состояние текущего продукта;
- owner-found bugs, visual fixes и небольшие general improvements делаются отдельными fix-ветками от актуального `main`;
- после выпуска `v0.3.0` такие изменения при необходимости выпускаются как `0.3.1`, `0.3.2`, ...;
- крупные новые market-data изменения в `main` до завершения R04 не попадают.

### `r04` — integration line будущего `0.4.0`

- создана от exact green baseline `b385e8cddfaa8e057dc34dc73a11d0bc839978d1`;
- каждая `R04-*` implementation task работает в отдельной task branch от актуального `r04`;
- accepted task merge идёт в `r04`, а не в `main`;
- `r04` может быть нестабильной между task gates, но accepted commits должны проходить обязательные проверки своей task-card.

### Forward-port fixes из `0.3.x`

Если дефект существует и в стабильной линии, и в `r04`:

1. исправить и принять его сначала в `main`;
2. при необходимости выпустить patch `0.3.x`;
3. после acceptance синхронизировать `main → r04` обычным merge;
4. разрешить конфликты в пользу сохранения как stable fix, так и уже принятого R04 scope;
5. запустить relevant tests/CI на новом `r04` HEAD.

Не делать независимые одинаковые исправления в обеих линиях без необходимости — это создаёт divergence.

Если дефект существует только в R04-коде, он исправляется только в `r04` task/fix branch.

### Финал 0.4

Перед release gate:

1. `main` должен содержать latest accepted `0.3.x` maintenance fixes;
2. latest `main` синхронизируется в `r04`;
3. R04 release gate выполняется на exact `r04` candidate HEAD;
4. после owner release command accepted `r04` интегрируется в `main`;
5. final exact-main CI должен быть green;
6. только после этого создаётся `v0.4.0` и GitHub Release.

## 2. Owner feedback / maintenance intake

Замечания владельца не обязаны ждать следующего большого релиза.

Классификация:

- **bug / financial correctness / data-loss / broken workflow** → stable maintenance, при необходимости patch release;
- **small visual/UX defect** → stable maintenance, если изменение локально и безопасно;
- **general improvement** → triage: `0.3.x` либо будущий release;
- **R04-specific behavior** → R04 backlog/fix;
- **new product idea** → issue/backlog, не расширяет текущий task scope автоматически.

GitHub Issues могут использоваться как owner-feedback inbox. Issue не становится release task автоматически: сначала triage, затем назначается target release/task-card.

# R04-01. MOEX market identity + quote semantics contract

**Priority:** P0  
**Status:** READY

До реализации зафиксировать нормативный контракт:

- какие instrument types поддерживаются первым релизом;
- canonical external identifiers и правила ISIN/SECID/board resolution;
- поведение при неоднозначном/отсутствующем mapping;
- какую market price/field считаем предлагаемой ценой для каждого поддержанного типа;
- timestamp/date semantics и timezone;
- stale-data policy;
- source/provenance representation;
- ручной override/exclusion semantics;
- поведение draft/closed months;
- network timeout/error/partial-result policy;
- отсутствие background refresh;
- тестовые synthetic examples без реальных портфельных данных.

**Acceptance:** R04-02…R04-07 могут реализовываться без самостоятельного придумывания market/financial semantics worker-моделью.
