## Дополнения к R03-14 — owner visual polish

**Priority:** P1  
**Executor:** Hermes  
**Reviewer:** Лера  
**Semantics:** presentation-only; финансовые формулы и persisted contracts не менять.

### R03-14A — единое форматирование чисел

Провести cross-app audit денежных и количественных значений.

- денежные суммы в display mode должны использовать shared formatter и группировку разрядов неразрывными пробелами;
- не должно оставаться user-facing денежных строк вида `123456` там, где ожидается `123 456`;
- проверить Dashboard, Analytics, Months, Month workspace, Goals, Accounts, Settings, badges, totals, table cells, tooltips и chart labels;
- editable inputs не форматировать так, чтобы ломать ввод/парсинг;
- не добавлять frontend financial math: задача только про presentation.

**Acceptance:** одинаковые display conventions для RUB на основных экранах; regression tests для formatter/ключевых presentation paths; visual smoke на 1366/1024/760.

### R03-14B — Month → Positions density/action hierarchy

Текущая таблица перегружена колонками и actions.

- `price_date` **сохранить в data contract**: это дата котировки, она может отличаться от `ReportingMonth.snapshot_date`;
- в create/edit flow по умолчанию использовать month snapshot date, как сейчас;
- на первом уровне таблицы не показывать дату цены постоянно, если она совпадает со snapshot date; отличающаяся дата должна оставаться доступной/заметной через secondary detail;
- источник цены также сделать secondary detail, кроме случаев, когда источник/отклонение действительно важно для интерпретации;
- `Средняя стоимость` переименовать/пояснить как **средняя цена приобретения за единицу**: это сохранённый input snapshot, а не автоматически восстановленная средняя из истории сделок;
- рыночная стоимость, себестоимость и нереализованный результат остаются calculated backend values;
- row actions: одна видимая primary/secondary action `Изменить`; destructive `Удалить` → `…` overflow с confirm;
- при edit не превращать строку в чрезмерно широкую форму; допускается dialog/drawer или compact edit presentation, если это проще и читаемее;
- НКД и price metadata остаются доступны, но не должны постоянно расширять каждую строку.

**Acceptance:** таблица читаема без налезаний на 1366 и 1024; 760 имеет аккуратный fallback; дата/источник не потеряны семантически; Edit/Delete behavior и position calculations не изменены.

### R03-14C — Month → Debts/Property density

- сократить первичный набор колонок до данных, необходимых для быстрого чтения;
- `В ликвидном капитале` не должен занимать широкую постоянную колонку: показать compact state/detail, особенно когда значение стандартное;
- destructive `Удалить` убрать из постоянной визуальной конкуренции и перенести в overflow/compact action pattern;
- аналогично проверить таблицу недвижимости: стоимость, ипотека, платёж должны читаться без столкновения с actions;
- никаких изменений debt/property formulas и include semantics.

**Acceptance:** debts/property не тесные на 1366/1024; длинные суммы не сталкиваются; actions не доминируют над данными; keyboard/focus/menu behavior preserved.

### R03-14D — Goals card width

- активные secondary goal cards не должны искусственно оставаться узкими при наличии большого свободного пространства;
- для небольшого числа активных целей предпочесть full-width/адаптивно широкие cards либо grid с разумным minimum width;
- блок `Сейчас / Цель / Осталось` должен сохранять денежные значения на одной читаемой строке там, где viewport это позволяет, без агрессивного переноса цифр;
- main/secondary visual hierarchy сохранить.

**Acceptance:** длинные monetary values в Goals читаются естественно на 1366/1024; нет огромной пустой половины layout при единственной secondary goal card; 760 остаётся одноколоночным.

# R03-16. Passive-income average eligibility contract

**Priority:** P0  
**Status:** DONE  
**Owner/executor:** Лера  
**Implementation:** отсутствует — contract/docs only  
**Depends on:** existing accepted C03 / `MASTER_SPEC §10.5`
**Normative ADR:** `docs/adr/0008-passive-income-history-eligibility.md`

## Проблема

Текущий accepted contract считает фактическое среднее по CLOSED reporting months: пока месяцев меньше 12 — по всем доступным CLOSED месяцам; после накопления 12 — rolling window последних 12 reporting months. Это **не calendar-year average**.

Следствие: исторический CLOSED месяц с нулевым passive income считается настоящим нулём. Это правильно для реального месяца без выплат, но искажает owner metric, если ранние reporting months были заведены только ради salary/tax history и не содержат полноценной инвестиционной истории.

Автоматически исключать все zero-income months нельзя: настоящий месяц с нулевым passive income должен оставаться в среднем.

## Принятый контракт

Зафиксирована одна глобальная включительная граница:

```text
passive_income_history_start_month: YYYY-MM | null
```

User-facing label: **«Учитывать пассивный доход начиная с …»**.

- `null` = backward-compatible all-history behavior;
- migration существующей БД и новый install получают `null`, ничего не определяется автоматически;
- CLOSED months до границы исключаются;
- eligible CLOSED months на/после границы входят независимо от суммы, включая настоящий ноль и отрицательное значение;
- DRAFT/reopened исключены до повторного закрытия;
- отсутствующий календарный месяц не становится нулём;
- окно = последние 12 eligible CLOSED reporting-month records, а не calendar year;
- произвольных per-month exclusion flags в 0.3 нет;
- один backend eligibility source используется C03 average, passive-income Goal current/progress и C04 actual-dividend history component;
- forward-looking `expected_cash_flows` этой границей не фильтруются;
- raw historical month data не удаляются и не переписываются;
- UI получает backend-derived count/window metadata и не фильтрует финансовую историю самостоятельно.

`MASTER_SPEC §9.1/§10.5/§10.6/§10.7` синхронизирован. Подробные примеры, migration semantics и rejected alternatives находятся в ADR 0008.

## Acceptance

- [x] обновлён `MASTER_SPEC §10.5` и добавлен ADR 0008;
- [x] однозначно определены default, migration/backward compatibility, CLOSED/reopen behavior и rolling-window selection;
- [x] синтетические примеры покрывают excluded historical month, eligible zero month, <12, >12, gap/draft/reopen и empty eligible window;
- [x] отдельно зафиксировано влияние на Goals и forecast dividend component;
- [x] implementation отсутствует.

# R03-17. Passive-income average eligibility implementation

**Priority:** P0  
**Status:** READY  
**Executor:** Hermes  
**Reviewer:** Лера  
**Route:** standard implementation from accepted ADR 0008; escalation only if migration/financial semantics diverge from R03-16.

## Сделать

Строго по ADR 0008:

- реализовать persisted logical setting `passive_income_history_start_month: YYYY-MM | null`;
- migration existing DB → `null`, без inference и без изменения текущего результата;
- passive-income average service использует единый eligibility source;
- Goal current value/progress и C04 actual-dividend component используют тот же source;
- forward-looking expected coupon/interest/other flows не фильтровать;
- Settings получает один простой control периода начала; Dashboard/Goals не создают собственные настройки;
- read DTO предоставляет `count_months`, `is_complete_12m`, configured boundary и backend-derived window/months-used metadata;
- Dashboard/Goals help показывает rolling semantics и фактически учтённое окно без технического текста;
- не добавлять произвольные per-month exclusions;
- только synthetic tests/fixtures.

## Acceptance

- migration preserves `null` and legacy result;
- month before boundary excluded; boundary month included;
- eligible CLOSED zero/negative included;
- missing calendar month не становится zero;
- DRAFT/reopened excluded, reclosed returns;
- при <12 eligible CLOSED months среднее делится на фактически учтённое число;
- при >12 используются последние 12 eligible CLOSED records;
- clearing boundary restores all-history behavior;
- passive-income Goal и C04 dividend component используют один selector;
- expected forward flows unaffected;
- money remains exact, no binary float;
- frontend не считает financial average/filter самостоятельно;
- backend targeted + broader tests green;
- Windows smoke подтверждает настройку и отображение `N из 12`;
- Лера принимает фактический diff.
