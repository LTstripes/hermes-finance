# ADR 0001: Архитектура локального финансового приложения

- **Статус:** принято
- **Дата:** 2026-08-04
- **Связанные документы:** [MASTER_SPEC](../MASTER_SPEC.md), [backlog](../HERMES_TASKS.md)

## Контекст

Finance Dashboard заменяет персональную Excel-модель локальным приложением с точными финансовыми расчётами, месячными снимками и проверяемой историей. MVP запускается на Windows одним владельцем, хранит данные локально и не требует облачной инфраструктуры или многопользовательской авторизации.

Архитектура должна:

- отделять финансовые правила от HTTP API и интерфейса;
- не допускать денежных расчётов через binary `float`;
- поддерживать миграции схемы и резервное копирование;
- позволять позднее перенести приложение на VPS без полной переработки домена;
- оставаться достаточно простой для личного объёма данных.

## Решение

### Репозиторий и границы

Используется monorepo с основными каталогами:

- `backend/` — Python-приложение, доменная логика, persistence и HTTP API;
- `frontend/` — React-приложение;
- `docs/` — спецификация, backlog и ADR;
- `scripts/` — команды разработки, миграции данных и локальной эксплуатации;
- `data/` — только локальные базы, импорты, экспорты и backup; содержимое не хранится в Git.

Backend разделяется на независимую доменную часть и внешние адаптеры. Финансовые формулы и бизнес-инварианты не зависят от FastAPI, SQLAlchemy или React. API вызывает доменные сервисы, а frontend получает уже рассчитанные показатели.

### Backend

Выбран стек:

- Python;
- FastAPI для HTTP API;
- Pydantic для входных и выходных контрактов;
- SQLAlchemy 2 для persistence;
- Alembic для версионируемых миграций;
- SQLite для локального MVP.

SQLite соответствует однопользовательской локальной нагрузке, не требует отдельного сервера и поддерживает транзакции и backup API. Foreign keys включаются явно.

### Frontend

Выбран стек:

- React;
- TypeScript;
- Vite;
- React Router;
- TanStack Query;
- Recharts;
- Tailwind CSS и простые компонентные примитивы.

Frontend отвечает за ввод, отображение и пользовательские состояния, но не дублирует финансовые формулы backend.

### Почему Excel не является базой

Excel остаётся источником разовой исторической миграции и визуальным референсом. Он не используется как рабочее хранилище, потому что:

- текущая книга содержит несогласованные диапазоны и ошибки формул;
- связи, ограничения и миграции схемы трудно контролировать;
- параллельное хранение исходных и расчётных значений непрозрачно;
- невозможно надёжно обеспечить транзакционное клонирование месяца и воспроизводимые расчёты.

После миграции источником истины становится SQLite; Excel не синхронизируется с приложением.

### Single-user и отсутствие авторизации

MVP предназначен для одного владельца и по умолчанию слушает только `127.0.0.1`. Регистрация, пароли, роли и удалённый доступ не добавляются заранее. Это уменьшает поверхность атаки и не создаёт инфраструктуру, которая не нужна локальному сценарию.

### Будущий переход на VPS

Переезд на VPS допускается в поздней версии без изменения доменной модели:

- конфигурация путей и окружения не зашивается в домен;
- API остаётся явной границей между frontend и backend;
- схема данных управляется Alembic;
- статический frontend может обслуживаться backend или reverse proxy;
- при реальной необходимости SQLite может быть заменён PostgreSQL через persistence-слой и миграционный план;
- авторизация, HTTPS, секреты и серверная backup strategy проектируются только перед внешним размещением.

VPS, PostgreSQL и авторизация не являются частью MVP 0.1.

## Последствия

### Положительные

- финансовая логика тестируется без HTTP и UI;
- локальный запуск остаётся простым;
- данные не зависят от Excel;
- миграции и backup становятся воспроизводимыми;
- будущий VPS не требует переписывать расчётный слой.

### Ограничения

- SQLite не предназначен для многопользовательской конкурентной записи;
- до появления авторизации приложение нельзя безопасно публиковать наружу;
- два отдельных dev-сервера требуют единых Windows-скриптов на следующем этапе;
- точность зависит от строго согласованных денежных и процентных контрактов, которые фиксируются до реализации доменных типов.

## Не принято этим ADR

ADR не добавляет новых функций и не определяет конкретную структуру Python-модулей, API endpoints, UI-компоненты или схему таблиц. Эти решения принимаются соответствующими задачами backlog.
